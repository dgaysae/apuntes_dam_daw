Entendemos por **desarrollo del software** a todo el proceso desde que se concibe una idea hasta que un programa está implementado en el ordenador y funcionando.

![ud02_ed_02_ciclo_desarrollo_software.png](/img/user/adjuntos/1DAM_ED/Unidad_02/ud02_ed_02_ciclo_desarrollo_software.png)

El proceso de desarrollo, que en un principio puede parecer una tarea simple, consta de una serie de pasos de obligado cumplimiento, pues sólo así podremos garantizar que los programas creados son eficientes, fiables, seguros y responden a las necesidades de los usuarios finales (aquellos que van a utilizar el programa).

La construcción de software es un proceso que puede llegar a ser muy complejo y que exige gran coordinación y disciplina del grupo de trabajo que lo desarrolle.

## 1.1. Clasificación del software

***Software*** es el "*conjunto de programas y datos necesarios para ejecutar una tarea en un ordenador*". Para parecer más interesantes, podemos traducirlo como **soporte lógico**, pero lo habitual es usar el término en inglés.

Frente al término *software* está el de ***hardware*** que hace referencia a todos los **elementos físicos** que componen el sistema informático (teclado, pantalla, CPU, impresora, discos, etc.).

A continuación, clasificamos el software según varios criterios.

### 1.1.1. Según el tipo de tarea que realiza

* **Software de sistema**: es el que controla y hace funcionar el hardware. Son los sistemas operativos (como Windows, Linux, Mac OS o Android) y los controladores de dispositivos (más conocidos como drivers), etc.

* **Software de aplicación**: son los programas que nos ayudan a hacer tareas específicas. Ejemplos de este tipo de software son los programas ofimáticos, aplicaciones de contabilidad, diseño asistido por ordenador, etc.

  Dentro de esta categoría podemos encontrar el **software de desarrollo**, que comprende a los programas que ayudan a los programadores en su tarea de escribir el código de los programas. Este **software de desarrollo** comprende una gran variedad de aplicaciones, como los **entornos de desarrollo integrados**  o <abbr title="Integrated Development Environment">IDE</abbr> que agrupan todas las herramientas útiles con una avanzada interfaz gráfica de usuario y muy versátiles entendiendo una gran variedad de lenguajes de programación.

### 1.1.2. Según la forma de distribuirlo

* **Shareware**: es el software que se distribuye de forma **gratuita con alguna limitación** (en cuanto a tiempo o funcionalidad) para que el usuario lo evalúe y, si es de su agrado y quiere disfrutar de la versión completa o sin límite de tiempo, deberá hacer un pago, generalmente pequeño.

  Ejemplos: [WinZip](https://www.winzip.com/), [WinRAR](https://winrar.es/), [Adobe Photoshop](https://www.adobe.com/es/products/photoshop.html), [IDM](https://www.internetdownloadmanager.com/) (*Internet Download Manager*) o [Malwarebytes](https://www.malwarebytes.com/es/).

* **Freeware**: gratuito. Suele incluir una licencia de uso que hace algunas restricciones, como la obligatoriedad de informar de quién es el autor y la prohibición de modificarlo o hacer negocio con él. La traducción correcta de Freeware es "software gratuito" y **no debe confundirse** con el "software libre" que veremos a continuación.

  Esta suele ser una confusión habitual derivada del hecho de que la palabra inglesa free se puede traducir como libre o como gratuito.

* **Adware**: que podría traducirse como software adjunto o añadido, es publicidad (en forma de anuncios o de software promocional) que acompaña a programas gratuitos. En ocasiones es posible evitarlos durante el proceso de instalación si estamos atentos. El usuario también tiene la posibilidad de adquirir las versiones de pago que estarán libres de Adware.

* **Software de uso específico**: es el software que se desarrolla a petición del cliente para un problema determinado. Estos programas están muy personalizados con los logos y los protocolos de funcionamiento de la empresa para la que va destinada.

### 1.1.3. Según la licencia

La licencia de un programa es el contrato en el que se establece el uso que el usuario final puede hacer de ese programa.

* **Software libre**: permite al usuario utilizarlo y distribuirlo libremente. La licencia más habitual en software libre es la Licencia Pública General o **<abbr title="General Public License">GPL</abbr>**.

* **Software libre de código abierto**: es software libre que se distribuye con el código fuente, de modo que el usuario también podrá estudiar su funcionamiento interno y modificarlo o añadir funcionalidad.

* **Software propietario**: es el software que se distribuye con rígidas condiciones de uso. Generalmente se prohíbe la redistribución, modificación, copia, ejecución simultánea en varias máquinas. Este software normalmente se distribuye en formato binario (es decir, sin acceso al código fuente) para hacer efectiva la prohibición de modificarlo. Sin embargo, el software propietario también puede ser gratuito o de pago.

* **Software de dominio público**: es el que no tiene ningún tipo de licencia y puede ser usado por cualquiera en la forma que desee. El motivo puede ser porque el autor sea desconocido o porque ha pasado el tiempo suficiente para que expiren los derechos de autor.

## 1.2. Ciclo de vida del software

Entendemos como ciclo de vida del software la serie de pasos a seguir para desarrollar un programa. Siempre se debe aplicar un modelo de ciclo de vida al desarrollo de cualquier proyecto software.

Son varios los modelos de ciclos de vida planteados desde el comienzo del desarrollo de software, pero los más significativos son los siguientes:

### Modelo en cascada
Es el modelo de vida clásico del software. Es prácticamente imposible que se pueda utilizar, ya que requiere conocer de antemano todos los requisitos del sistema. Sólo es aplicable a pequeños desarrollos, ya que las etapas pasan de una a otra sin retorno posible (se presupone que no habrá errores ni variaciones del software).

![ud02_ed_03_modelo_en_cascada.png](/img/user/adjuntos/1DAM_ED/Unidad_02/ud02_ed_03_modelo_en_cascada.png)

### Modelo en cascada con realimentación

Es uno de los modelos más utilizados. Proviene del modelo anterior, pero se introduce una **realimentación entre etapas**, de forma que podamos volver atrás en cualquier momento para corregir, modificar o depurar algún aspecto. No obstante, si se prevén muchos cambios durante el desarrollo no es el modelo más idóneo. Es el modelo perfecto si el proyecto es rígido (pocos cambios, poco evolutivo) y los requisitos están claros.

![ud02_ed_04_modelo_en_cascada_con_retroalimentacion.png](/img/user/adjuntos/1DAM_ED/Unidad_02/ud02_ed_04_modelo_en_cascada_con_retroalimentacion.png)

### Modelos evolutivos

Son más jóvenes que los anteriores. Tienen en cuenta la **naturaleza cambiante y evolutiva** del software. Distinguimos dos variantes:

1. **Modelo Iterativo Incremental**: está basado en el modelo en **cascada con realimentación**, donde las fases se repiten y refinan, y van propagando su mejora a las fases siguientes. Combina el diseño iterativo con la entrega incremental.
  
  Se trata de un enfoque de **desarrollo ágil** donde se construye un producto en ciclos repetidos o iteraciones. En **cada iteración se repite el ciclo** de análisis, diseño, desarrollo y pruebas para entregar al final de dicha iteración una versión funcional del producto.
  
  En cada ciclo se añaden nuevas funcionalidades (incrementos) **basándose en el *feedback*** recibido en el ciclo anterior. Cada entrega ofrece un **<abbr title="Minimum Value Product">MVP</abbr>** o **producto mínimo viable** con pocas funcionalidades pero consolidadas y probadas.
  
  De esta forma se puede entregar un producto funcional rápidamente, minimizando riesgos y adaptándose a los cambios a través de la mejora continua del producto con cada entrega.

  ![ud02_ed_05_modelo_iterativo_incremental.png](/img/user/adjuntos/1DAM_ED/Unidad_02/ud02_ed_05_modelo_iterativo_incremental.png)

2. **Modelo en espiral**: es una combinación del modelo anterior con el modelo en cascada. En él, el software se va construyendo repetidamente en forma de versiones que son cada vez mejores, debido a que incrementan la funcionalidad en cada versión.
  
  Se repite a través de ciclos o "espirales", cada una con fases de planificación, análisis de riesgos, ingeniería (desarrollo) y evaluación. Cada fase ofrece una versión del producto.
  
  La clave está en el **análisis de riesgos** para decidir los siguientes pasos, minimizando errores y permitiendo agregar funcionalidad de forma progresiva y segura hasta que el producto esté completo.
  
  Este es uno de los modelos más complejos.

## 1.3. Roles del desarrollo del software

### Arquitecto de software

- Decide cómo se realiza el proyecto y cómo va a estructurarse.

- Tiene un amplio conocimiento de las tecnologías, los frameworks y las librerías.

- Decide y forma los recursos del desarrollo de un proyecto

### Jefe de proyecto

- Dirige el curso del proyecto.

- Puede ser un analista con experiencia, un arquitecto o una persona dedicada a ese puesto en exclusividad.

- Debe saber gestionar un equipo y lidiar con los tiempos.

- Trata de manera continua y fluida con el cliente

### Analista funcional

El analista funcional trabaja en el nivel más alto y se enfoca en las **necesidades del usuario y del negocio**. Actúa como enlace entre el cliente (o los *stakeholders*) y el equipo técnico.

| Aspecto | Responsabilidad Clave | Enfoque |
| ----- | ----- | ----- |
| **Pregunta Clave** | **¿Qué debe hacer el sistema?** | Las necesidades del negocio. |
| **Rol Principal** | **Definición de Requisitos.** | Recopila, analiza y documenta los **requisitos funcionales** (lo que el usuario puede hacer con el sistema) y no funcionales (rendimiento, seguridad). |
| **Documentación** | **Análisis Funcional** o **Especificación de Requisitos Funcionales (ERF).** | Define casos de uso, flujos de trabajo y el comportamiento deseado de la aplicación. |
| **Conocimiento** | **Negocio (Dominio).** | Debe entender a fondo el sector o el proceso de negocio que el software debe automatizar o mejorar. |
| **Herramientas** | Entrevistas, modelado de procesos (BPMN), *story mapping*. |  |

### Analista orgánico

El analista orgánico trabaja en el **nivel de diseño técnico** y se enfoca en la **implementación** concreta de las funciones. Actúa como el arquitecto de la solución de software.

| Aspecto | Responsabilidad Clave | Enfoque |
| :---- | :---- | :---- |
| **Pregunta Clave** | **¿Cómo se va a implementar técnicamente?** | La estructura interna del software. |
| **Rol Principal** | **Diseño Técnico.** | Traduce el análisis funcional en un diseño detallado del sistema, incluyendo su estructura, componentes y tecnología a utilizar. |
| **Documentación** | **Análisis Orgánico** o **Diseño Técnico.** | Especifica la arquitectura del *software*, diseño de base de datos (modelo de datos), diagramas **UML** (clases, secuencias) y la definición de las interfaces entre componentes. |
| **Conocimiento** | **Tecnología (Técnico).** | Debe tener un conocimiento profundo de programación, bases de datos, arquitecturas de software (*frameworks*), y *hardware*. |
| **Herramientas** | UML (Rational Rose o similar), lenguajes de programación, herramientas de modelado de datos. |  |

> [!tip] Importante 
> Las diferencias entre un analista funcional y uno orgánico se centran en el alcance de cada uno y en las preguntas clave que intentan responder dentro del ciclo de desarrollo de software: el funcional se enfoca en el "qué" y el orgánico en el "cómo".

Ambos perfiles son cruciales, ya que el analista funcional define los requerimientos de negocio, y el analista orgánico traduce esos requerimientos a un diseño técnico ejecutable por los programadores.

### Programador

- Conoce en profundidad el lenguaje de programación.

- Se encarga de codificar las tareas encomendadas por el analista orgánico.

- Su misión es la de codificar y probar los diferentes módulos de la aplicación.

### Tester

- No requiere conocimientos de programación.

- Se encarga de comprobar el funcionamiento de los programas.

- Debe conocer en profundidad el funcionamiento de la aplicación a nivel de cliente.

## 1.4. Metodologías ágiles en la gestión de proyectos

La metodología ágil es un **enfoque** para la gestión de proyectos y el desarrollo de software que se caracteriza por su **flexibilidad**, **colaboración** y **adaptación continua**. En lugar de seguir un plan rígido y detallado desde el principio, las metodologías ágiles permiten a los equipos trabajar de manera más **iterativa** y **colaborativa**, lo que les permite responder a los cambios y desafíos a medida que surgen. Algunos de los frameworks ágiles más conocidas incluyen [**Scrum**](https://es.wikipedia.org/wiki/Scrum_\(desarrollo_de_software\)) y [**Kanban**](https://es.wikipedia.org/wiki/Kanban) entre otras.

Los principios y características comunes en las metodologías ágiles son:

* **Colaboración y comunicación**: las metodologías ágiles promueven la colaboración cercana entre los miembros del equipo, así como la comunicación frecuente con los stakeholders (partes interesadas) del proyecto.

* **Iteración**: el trabajo se divide en iteraciones o ciclos de desarrollo cortos y enfocados, generalmente de una a cuatro semanas de duración. Al final de cada iteración, se entrega un producto funcional o una parte de él.

* **Priorización**: las tareas y características se priorizan según su valor para el cliente o el proyecto. Esto permite a los equipos centrarse en lo más importante primero.

* **Flexibilidad**: las metodologías ágiles están diseñadas para adaptarse a los cambios. Los requisitos pueden cambiar a lo largo del proyecto, y las metodologías ágiles permiten incorporar estos cambios de manera eficiente.

* **Entrega continua**: se busca entregar partes funcionales del producto en forma regular. Esto permite obtener retroalimentación temprana y realizar ajustes en consecuencia.

* **Autoorganización del equipo**: los equipos ágiles son responsables de la planificación y la toma de decisiones. Se espera que sean autoorganizados y autogestionados.

* **Visión del cliente**: se enfoca en satisfacer las necesidades del cliente y en la entrega de valor continuo. La retroalimentación del cliente es fundamental.

* **Medición y mejora continua**: se fomenta la evaluación constante del proceso y la búsqueda de mejoras en la productividad y la calidad.


## 1.5. Herramientas de apoyo al desarrollo del software

En la práctica, para llevar a cabo varias de las etapas vistas en el punto anterior, contamos con las herramientas informáticas, cuya finalidad principal es **automatizar las tareas** y con ello ganar **fiabilidad** y **tiempo**. 

Esto nos va a permitir centrarnos en los requerimientos del sistema y en el análisis del mismo, que son las causas principales de los fallos del software. 

Las **herramientas CASE** (*Computer-Aided Software Engineering*) son un conjunto de aplicaciones que se utilizan en el desarrollo de software con el objetivo de **reducir costes** y **tiempo del proceso**, mejorando por tanto la productividad del proceso.

Estas herramientas nos pueden ayudar en el diseño del proyecto, en la codificación de nuestro diseño a partir de su apariencia visual, detección de errores… 

El **desarrollo rápido de aplicaciones** o **RAD** (*Rapid Application Development*) es un proceso de desarrollo de software que comprende el **desarrollo iterativo**, la construcción de **prototipos** y el uso de **utilidades CASE**. Hoy en día se suele utilizar para referirnos al desarrollo rápido de interfaces gráficas de usuario o entornos de desarrollo integrado completos.

La tecnología CASE trata de automatizar las fases del desarrollo de software para que mejore la calidad del proceso y del resultado final. 

En concreto, estas herramientas permiten: 

* **Mejorar la** **planificación** del proyecto. 

* Darle **agilidad al proceso**. 

* Poder **reutilizar partes del software** en proyectos futuros. 

* Hacer que las aplicaciones **respondan a estándares**. 

* **Mejorar** la tarea del **mantenimiento** de los programas. 

* **Mejorar el proceso de desarrollo**, al permitir visualizar las fases de forma gráfica.

El concepto de herramientas CASE ha evolucionado significativamente desde que aparecieron. El término "*herramientas CASE*" en la actualidad abarca una amplia gama de aplicaciones de software que asisten en diversas fases del **ciclo de vida del desarrollo de software** o **SDLC** (*Software Development Life Cycle*). Sin embargo, su funcionalidad tradicional se ha integrado o ha evolucionado en herramientas modernas y especializadas.

### 1.5.1. Clasificación

Las herramientas CASE fueron diseñadas para automatizar tareas en el SDLC y se pueden clasificar de varias formas.

Normalmente, las herramientas CASE se clasifican **en función de las fases del ciclo de vida del software** en la que ofrecen ayuda: 

* **U-CASE**: ofrece ayuda en las fases de **planificación** y **análisis de requisitos**. 

* **M-CASE**: ofrece ayuda en **análisis** y **diseño**. 

* **L-CASE**: ayuda en la **programación del software**, **detección de errores** del código, **depuración** de programas y **pruebas** y en la **generación de la documentación** del proyecto.

Otra forma de clasificar las herramientas CASE puede ser la siguiente:

![ud02_ed_07_clasificacion_herramientas_CASE.png](/img/user/adjuntos/1DAM_ED/Unidad_02/ud02_ed_07_clasificacion_herramientas_CASE.png)

Donde:

* **Upper CASE** (planificación, análisis y diseño): estas herramientas se centran en el **modelado** y la **especificación**.

  Siguen siendo muy relevantes en la actualidad, como las herramientas para la creación de diagramas **UML** ([StarUML](https://staruml.io/), [Visual Paradigm](https://www.visual-paradigm.com/) o [Astah](https://astah.net/)) y el modelado de **bases de datos**.

* **Lower CASE** (implementación, pruebas y mantenimiento): se enfocan en la generación de código y la verificación.

  En la práctica estas funciones han sido asumidas por los IDE (*Integrated Development Environment*) o entornos de desarrollo integrados avanzados (como [Visual Studio](https://visualstudio.microsoft.com/es/), [Eclipse](https://eclipseide.org/) o [IntelliJ IDEA](https://www.jetbrains.com/idea/download/)) y herramientas de **Integración/Despliegue Continuos** (<abbr title="Continuous Integration">CI</abbr>/<abbr title="Continuous Deployment">CD</abbr>).

* **Integrated CASE** (I-CASE): su intención es cubrir todo el ciclo de vida. Plataformas como [GeneXus](https://www.genexus.com/es/productos/genexus/versiones/genexus17/videos/que-es-genexus)[^1] o [Appian](https://appian.com/es/about/explore/overview) (ambas plataformas Low-Code) son ejemplos de entornos integrados que automatizan el desarrollo de principio a fin.

Existen muchas herramientas CASE en la actualidad y la mayoría de los entornos de desarrollo de software (NetBeans, Eclipse…) incluyen utilidades para las distintas fases de desarrollo del software.

### 1.5.2. Integración y automatización con IA

El concepto CASE se ha fusionado con tendencias tecnológicas actuales, haciéndolo aún más potente:

* Modelado con **generación de código**: herramientas como **Enterprise Architect AI** o **Visual Paradigm** han evolucionado para que los modelos de diseño (UML, BPMN) no solo documenten, sino que **generen automáticamente fragmentos de código**, acelerando el proceso.

* **Asistencia por inteligencia artificial**: la funcionalidad **lower CASE** de generación de código ha sido revolucionada por la inteligencia artificial generativa. Asistentes como [**Claude Code**](https://code.claude.com/), [**Codex**](https://openai.com/es-ES/codex/), [**OpenCode**](https://opencode.ai/) o [**GitHub Copilot**](https://github.com/features/copilot) y entornos como [**Cursor IDE**](https://cursor.com/) **no son CASE** en el sentido tradicional, pero cumplen el **objetivo principal de CASE**: **automatizar la codificación** y **reducir errores**.

* **Plataformas** **Low-Code/No-Code**: plataformas como [**Appian**](https://appian.com/es/about/explore/overview), [**GeneXus**](https://www.genexus.com/es/productos/genexus/versiones/genexus17/videos/que-es-genexus) o [**Babel AI**](https://www.babel.ai/) se consideran, en cierto modo, una evolución del concepto I-CASE, ya que permiten a los usuarios crear sistemas funcionales a partir de especificaciones y modelos visuales, sin código manual o con muy poco.

### 1.5.3. Correlación de CASE tradicional con herramientas actuales

En lugar de depender de una única herramienta CASE monolítica, los equipos actuales utilizan un conjunto integrado de herramientas especializadas que, en conjunto, cubren las funciones originales de CASE:

| Función CASE tradicional | Herramientas actuales y específicas |
| :---- | :---- |
| Modelado de requisitos/diseño (Upper CASE) | Enterprise Architect, Visual Paradigm, Lucidchart, Microsoft Visio, StarUML |
| Desarrollo y codificación (Lower CASE) | IDEs como Visual Studio Code, IntelliJ, Eclipse; Asistentes de IA como GitHub Copilot |
| Gestión de proyectos/repositorio (Depósito Central) | Jira, Trello, **GitHub**, GitLab (que cumplen el rol de repositorio central de artefactos) |
| Pruebas y QA (Lower CASE) | Selenium (automatización web), **JUnit** (pruebas unitarias), Postman (pruebas de API) |
| Generación de código | Plataformas Low-Code/No-Code (Appian, Mendix, OutSystems) |

La conclusión es que el concepto de ingeniería de software asistida por computadora (CASE) que es la automatización de las tareas del desarrollo, está más vivo que nunca, integrado en las **modernas pilas de desarrollo**, las **herramientas de colaboración** y la **IA**.


[^1]:  Es una plataforma de desarrollo de software Low-Code que automatiza y simplifica la creación, evolución y mantenimiento de aplicaciones empresariales multiplataforma usando Inteligencia Artificial (IA) para generar código y bases de datos a partir del conocimiento del negocio.
