El **`RecyclerView`** es un componente avanzado y flexible que sustituye al antiguo **`ListView`**. Su propósito principal es mostrar grandes conjuntos de datos de forma eficiente, sin lags ni pantallas congeladas esperando el refresco de información.

A diferencia de otros componentes, el `RecyclerView`no crea una vista por cada elemento de la lista (lo que consumiría mucha memoria). En su lugar, "recicla" las vistas que salen de la pantalla y las reutiliza para los nuevos elementos que entran al hacer scroll. Esta vista reciclada se conoce como **ítem**.

Los **componentes necesarios** para un `RecyclerView` son:

1. **Data Class**: modelo de lo que queremos mostrar.  
2. **XML del Ítem**: diseño de una única fila/celda.  
3. **ViewHolder**: contiene las referencias a las vistas de cada ítem.  
4. **Adapter**: como hemos comentado en clase, el adapter es el mecanismo que permite introducir un conjunto de datos de cualquier tipo (incluso de nuestras propias clases) a las vistas.

# 7.1. Creación del modelo de datos

Para el ejemplo del vídeo (ver [[Asignaturas/2DAM_PMDM/Apuntes/Unidad 06/30. Referencias#Tutorial RECYCLERVIEW DEFINITIVO en ANDROID - AristiDevs\|Referencias]]) definimos una **`data class`** que representa la información necesaria.

```kotlin
// Archivo: Superhero.kt
data class Superhero(
    val superhero: String,
    val publisher: String,
    val realName: String,
    val photo: String // URL de la imagen
)
```

Diseño de la Interfaz del ítem

Debemos crear un archivo de diseño separado (ej. item_superhero.xml) para definir **cómo se verá el ítem**, que representa la vista de **cada fila**. Es recomendable usar **`CardView`** [[12:57](http://www.youtube.com/watch?v=k3zoVAMuW5w&t=777)] para un acabado visual más profesional y **`ConstraintLayout`** [[41:45](http://www.youtube.com/watch?v=k3zoVAMuW5w&t=2505)] para organizar los elementos.

> [!warning] Cuidado
> El atributo **`android:layout_height`** del contenedor raíz en este XML debe ser `wrap_content`. Si se pone `match_parent`, cada ítem ocupará toda la pantalla. [[16:00](http://www.youtube.com/watch?v=k3zoVAMuW5w&t=960)]

# 7.2. Adapter y ViewHolder

El `adapter` es el elemento principal del `RecyclerView`. Debe heredar de **`RecyclerView.Adapter`** y especificar su **`ViewHolder`**. [[08:54](http://www.youtube.com/watch?v=k3zoVAMuW5w&t=534)]

Para implementar el adapter prestamos atención a:

* **`onCreateViewHolder`**: expande (infla) el layout del ítem y lo pasa al `ViewHolder`. [[12:14](http://www.youtube.com/watch?v=k3zoVAMuW5w&t=734)]

* **`onBindViewHolder`**: se encarga de enlazar cda dato de un objeto específico a su correspondiente espacio (`TextView`, `EditText`, `ImageView`, etc.) en alguna parte del ítem. [[22:31](http://www.youtube.com/watch?v=k3zoVAMuW5w&t=1351)]

* **`getItemCount`**: devuelve el tamaño de la lista de datos. [[11:36](http://www.youtube.com/watch?v=k3zoVAMuW5w&t=696)]

En términos simples, un **`ViewHolder`** es un "contenedor" que guarda las referencias de las vistas de **un sólo ítem** de la lista.

Imagina que tu lista tiene una imagen, un título y un subtítulo. Sin un `ViewHolder`, cada vez que el sistema tuviera que mostrar una fila al hacer scroll, tendría que ejecutar el método `findViewById()` tres veces. Y si tienes 1000 elementos... se **consumirían muchísimos recursos** y la aplicación se quedaría congelada.

El `ViewHolder` soluciona esto memorizando dónde están esos elementos la primera vez que se crean. Veamos cómo funciona:

1. En lugar de buscar los elementos por su ID cada vez, el `ViewHolder` los busca **una sola vez** al crearse y los guarda en variables.

2. Cuando una fila sale por la parte superior de la pantalla, el `RecyclerView` no la destruye. Simplemente toma ese "contenedor" (el `ViewHolder`), le cambia los datos (el texto, la imagen) y lo mete por la parte inferior.

3. Gracias a esto, el scroll es suave porque el sistema **sólo tiene que actualizar el contenido**, no buscar los componentes en el layout XML de nuevo.

Veamos el ejemplo del `ViewHolder` con `ViewBinding` del vídeo. Es importante observar cómo las vistas se asignan a constantes dentro de la clase:

```kotlin
class GameViewHolder(view: View) : RecyclerView.ViewHolder(view) {
    /*
    Usamos ViewBinding para referenciar las vistas del
    XML 'item_game.xml'
    */
    private val binding = ItemGameBinding.bind(view)

    fun render(game: Game) {
        /*
        Aquí "atamos" los datos al contenedor que ya tiene
        las referencias guardadas
        */
        binding.tvTitle.text = game.title
        binding.tvPlatform.text = game.platform
        
        /*
        No hace falta hacer findViewById, 'binding' ya sabe
        dónde están
        */
        Glide
            .with(binding.ivCover.context)
            .load(game.coverUrl)
            .into(binding.ivCover)
    }
}
```

Teniendo en cuenta que un móvil es una máquina con muchas más limitaciones que un ordenador, las ventajas son considerables:

1. **Ahorro de batería y CPU**, ya que evita operaciones costosas de búsqueda en el layout.

2. Es mucho más **fluido**. Permite que el scroll ocurra a 60 (o 120) fotogramas por segundo.

3. A diferencia del antiguo `ListView`, en el `RecyclerView` es obligatorio usar el patrón ViewHolder por diseño de la API.

## 7.3. Activity - ViewBinding

Para conectar el RecyclerView en nuestra Activity, activamos primero **`ViewBinding`** en el archivo `build.gradle` (nivel app). [[29:43](http://www.youtube.com/watch?v=k3zoVAMuW5w&t=1783)]  

```kotlin
buildFeatures {
   viewBinding = true
}
```

```kotlin
// Configuración en la Activity
private fun initRecyclerView() {
    val manager = LinearLayoutManager(this)
    binding.recyclerSuperhero.layoutManager = manager
    binding.recyclerSuperhero.adapter =
                SuperheroAdapter(SuperheroProvider.superheroList)
}
```

Para cargar imágenes desde una URL, utilizamos la librería **Picasso** o **Glide**. [[26:40](http://www.youtube.com/watch?v=k3zoVAMuW5w&t=1600)]

> [!warning] Cuidado
> Esto requiere que nuestra aplicación tenga permisos para acceder a Internet. Por tanto, hay que indicarlo así en el fichero `AndroidManifest.xml`.

## 7.4. Eventos

La forma más profesional y escalable de gestionar clics es pasar una función **Lambda** desde la `Activity` al `Adapter`. [[35:11](http://www.youtube.com/watch?v=k3zoVAMuW5w&t=2111)]

```kotlin
// En el Adapter
class SuperheroAdapter(
    private val superheroList: List<Superhero>,
    private val onClickListener: (Superhero) -> Unit // Lambda
) : RecyclerView.Adapter<SuperheroViewHolder>() { ... }

// En el ViewHolder (dentro de la función render)
itemView.setOnClickListener { onClickListener(superheroModel) }
```

## 7.5. Personalización: LayoutManagers y Decoradores

Podemos cambiar la disposición de la lista sin tocar el adaptador, solo cambiando el **`LayoutManager`**: [[40:43](http://www.youtube.com/watch?v=k3zoVAMuW5w&t=2443)]

* **`LinearLayoutManager`**: lista vertical u horizontal.  
* **`GridLayoutManager`**: rejilla (ej. 2 columnas).

Para añadir líneas divisorias, usamos un **`ItemDecoration`**: [[39:32](http://www.youtube.com/watch?v=k3zoVAMuW5w&t=2372)]

```kotlin
val decoration = DividerItemDecoration(this, manager.orientation)
binding.recyclerSuperhero.addItemDecoration(decoration)
```

## 7.6. Mejoras y Actualizaciones: ListAdapter y DiffUtil

En el vídeo se usa `notifyDataSetChanged()` para refrescar la lista, pero en versiones más actuales de Android (2022-presente), se recomienda usar **`ListAdapter`** y **`DiffUtil`**.

El motivo es que `notifyDataSetChanged()` **redibuja toda la lista** aunque solo cambie un elemento. **`DiffUtil`** calcula qué elementos han cambiado exactamente y solo actualiza esos, lo que mejora drásticamente el rendimiento y permite animaciones automáticas.
